## 4. g11 の調査結果(根本原因)

引き継ぎ時の疑い「タップは数えたのに着地拒否が増えない」は、アプリの欠陥ではなかった。

1. **H8-D の「取り違え防止の確認」は仕様どおりの動作**。低 FPS(CI は約 9〜11fps)では目印が画面上で動き、タップが「確認待ち」になる。確認待ちは着地開始でも拒否でもない(記録上は `tap → ask`)。テストはこれを想定していなかった。
   → 確認ボタンに答える `tapConfirm` を追加し、確認待ちも「押した対象ID に紐づいた結果」としてのみ認めた。
2. **テストの時計のずれ**。CDP の `touchStart → sleep(60) → touchEnd` は、遅い実行環境では往復の遅れで実時間が 500〜800ms に延び、アプリが正しく「長押し」と判定した(`upSlow dt=551/780`)。これが g11 (F)、g13 の「タップ不認識」に見えていた。
   → `virtualTouch`(CDP の `timestamp` に意図した時刻を付ける)で指の時間を決め打ちにした。アプリの判定の閾値は変えていない。CDP の timestamp が `event.timeStamp` に反映されることは別スクリプトで実測した(送信の間に実時間 400ms 空けても差が 60.0ms)。
3. **接近開始後に目印の位置が変わる**。接近中は鳥が目印の方へ向きを変えるので、最初に読んだ座標を押しても外れる。外れた「取消しのタップ」が届かず、次のテストが前の接近を引きずった(連鎖失敗)。
   → 押す直前に位置を読み直す。
4. **g12(shard 5)の標本数**: 描画が遅い環境では、指が届く前に足場を通り過ぎる試行が約 3 割出る。往復を 1 回にし、種類ごとの試行を 2 → 3 回に増やした。合格の閾値(開始 6 件以上、成功率 40%以上)は変えていない。
5. **g10 の「草が道路に透ける」判定**: 300m 地点の値が 0.01〜0.024 で揺れ、閾値 0.02 に近かった(main と無関係なファイルのみで、この branch で悪化したものではない)。昼夜の進みで色が変わるのが一因とみて、テストで時刻を正午に固定した。固定後のローカルは 0.0161〜0.0194。**余裕は小さい**。

禁止事項(skip・閾値の緩和・sleep の延長)は行っていない。変更は `test/browser.mjs` のみ(+ `CHROME_PATH` による実行ファイル指定)。`src/main.ts` には診断用の `spotTapLog` を追加した(動作は変えない)。

## 5. 再現条件(ローカル)

```
npm ci && npm run build
CHROME_PATH=<headless_shell のパス> THROTTLE=10 node test/browser.mjs --only g11 --port 4211
```

- `THROTTLE=n`: CDP の CPU 絞り。10 倍で CI の失敗(目印までの距離 34m、拒否 3)が再現した。
- 並列で走らせるなら `--port` を分ける。5 本以上の並列は CPU 不足で g7 の歩行距離などが落ちる(負荷の影響で、CI の失敗とは別物)。
- THROTTLE=6 以上では「目印の描画コスト < 3ms」が落ちる。これは絞った CPU の時間測定で、CI では出ない。

## 6. endurance

- CI の endurance は PR では skipped(main への push と手動実行のみ)。同名ワークフローを同じ ref で手動実行すると、実行中の PR 用 CI が取り消されるため、PR 上では実施していない。
- 代わりにローカルで `npm run test:endurance`(30 分 × 4 方針 × 3 シード = 360 分)を実行: テレポート 0、範囲外 0、建物の中 0、固着 0、クラッシュ 16、着地 180、`endurance checks passed`。実施時のソースは d3b8535 前後(以降の変更はテストファイルのみ)。
- main への統合前に CI の endurance(`workflow_dispatch`)でも確認すること。
