## 4. g11 の調査結果(根本原因)

引き継ぎ時の疑い「タップは数えたのに着地拒否が増えない」は、アプリの欠陥ではなかった。

1. **H8-D の「取り違え防止の確認」は仕様どおりの動作**。低 FPS(CI は約 9〜11fps)では目印が画面上で動き、タップが「確認待ち」になる。確認待ちは着地開始でも拒否でもない(記録上は `tap → ask`)。テストはこれを想定していなかった。
   → 確認ボタンに答える `tapConfirm` を追加し、確認待ちも「押した対象ID に紐づいた結果」としてのみ認めた。
2. **テストの時計のずれ**。CDP の `touchStart → sleep(60) → touchEnd` は、遅い実行環境では往復の遅れで実時間が 500〜800ms に延び、アプリが正しく「長押し」と判定した(`upSlow dt=551/780`)。これが g11 (F)、g13 の「タップ不認識」に見えていた。
   → `virtualTouch`(CDP の `timestamp` に意図した時刻を付ける)で指の時間を決め打ちにした。アプリの判定の閾値は変えていない。CDP の timestamp が `event.timeStamp` に反映されることは別スクリプトで実測した(送信の間に実時間 400ms 空けても差が 60.0ms)。
3. **接近開始後に目印の位置が変わる**。接近中は鳥が目印の方へ向きを変えるので、最初に読んだ座標を押しても外れる。外れた「取消しのタップ」が届かず、次のテストが前の接近を引きずった(連鎖失敗)。
   → 押す直前に位置を読み直す。
4. **g12(shard 5)の標本数**: 描画が遅い環境では、指が届く前に足場を通り過ぎる試行が約 3 割出る。往復を 1 回にし、種類ごとの試行を 2 → 3 回に増やした。合格の閾値(開始 6 件以上、成功率 40%以上)は変えていない。
5. **g10 の「草が道路に透ける」判定**: 300m 地点の値が 0.01〜0.024 で揺れ、閾値 0.02 に近かった(main と無関係なファイルのみで、この branch で悪化したものではない)。昼夜の進みで色が変わるのが一因とみて、テストで時刻を正午に固定した。固定後のローカルは 0.0161〜0.0194。**余裕は小さい**。

禁止事項(skip・閾値の緩和・sleep の延長)は行っていない。変更は `test/browser.mjs` のみ(+ `CHROME_PATH` による実行ファイル指定)。`src/main.ts` には診断用の `spotTapLog` を追加した(動作は変えない)。

### 9.2 根本原因(「テストの時計」と「ゲーム内の時間」のずれ)

- ゲームは 1 フレームに最大 0.1 秒・6 ステップしか進まない(`MAX_FRAME`、`MAX_STEPS`)。描画が約 10fps を下回ると、**ゲーム内の時間は実時間より遅く進む**。実測(このコンテナ、CPU 絞りなし): ゲーム内 1 秒あたり実時間 約 0.56 秒の進み、絞り 10 倍で 0.44。CI は約 9〜11fps でほぼ実時間。
- 古いテストは実時間の `sleep`(保持・待ち)で「歩く」「押す」を測っていたため、遅い環境では進行が足りず落ちた。**アプリの欠陥ではなく、測り方のずれ**(main でも同じ負荷で落ちる項目がある)。

## 10. g8「約 90 度旋回」の不安定性(2026/11/15)

### 10.1 問題
g8「リングの右へ滑らせると約 90 度右へ向く」が、約 -79 度となって失敗することがあった(`897126a` の CI、main の `0072aff` でも同じ項目が失敗)。判定は -80〜-100 度。

### 10.2 原因(評価時点のずれ。旋回性能の問題ではない)
- 仕様(`src/proxpad.ts`、`src/flight.ts` の `proxAir`): リング右側(環状)に指を置くと、目標の向きは触れ始めの向きから 90 度右。機首は目標へ `rate = clamp(誤差 × turnGain, ±turnRate)` で回るので、**目標へ指数的に近づく**。
- 旧テストは「向きの変化が 68.8 度(-1.2 rad)を超えたら待ちをやめ、直後に角度を読む」。68.8 度は旋回の途中の値で、読み取りの時点で結果が変わる。
- 1 ステップごとに記録した旋回曲線(超えたステップを 0 として): **+0.05 秒 → -78.9 度、+0.1 秒 → -83.6 度、+0.2 秒 → -87.9 度、+0.5 秒 → -89.9 度、最終 -90.0 度**。CI の -79 度は、超えた約 0.05 秒後(3 ステップ後)に読んだ場合と一致する。
- ゲームは 1 フレームに最大 0.1 秒(6 ステップ)まで進めるので、「超えたフレームから読むまでのゲーム内時間」はフレームの揺れで 0.05〜0.1 秒に変わる。ローカルの単独実験(各 14 回、CPU 1 倍・6 倍)では、読み取りは常に超えた 0.1 秒後で、-84.6 度、範囲外 0 件、落ち着いた角度は 14 回とも -90 度だった。CI では 0.05 秒後に当たる回が時々ある、という説明になる。

### 10.3 main との比較
main(c29213a)と H9 で、同じ条件(同じ入力・同じ開始状態)の旋回曲線は、全時点で小数第 1 位まで一致した。**H9(低速巡航)は旋回性能を変えていない。H9 固有の回帰ではなく、既存のテストの評価時点の問題。**

### 10.4 修正(`test/browser.mjs` の g8 のみ。アプリは変更なし)
- 評価を「旋回が目標に達した」状態にゲーム状態で連動させた: 向きの変化が -1.2 rad を超え、**かつ**目標の向きとの差が約 1.1 度(0.02 rad)未満になったとき。判定範囲(-80〜-100 度)は不変。skip と、判定範囲・成功率の閾値の緩和は行っていない。**待機の上限は長くした**(下の項目の「待ちの上限を 60 秒の保険に」を含む。一覧は §11.1。当初ここに書いた「タイムアウトの延長は行っていない」は不正確だったので訂正する)。
- 同じ g8 の中の、実時間で待つ同種の 3 項目も、ゲーム内時間と状態で待つ方式に直した: 指を離したあとの前進(1.5 秒)、上のパッドでの歩行(1.2 秒)、地上の長押しの跳ね上がり(0.4 m を超えるまで状態で待つ)・戻り(待ちの上限を 60 秒の保険に)。これらはローカルの CPU 1 倍の単独実行でも落ちる回があった(このコンテナのゲーム内時間は実時間の約 0.5 倍)。CI ではこれまで落ちていない。

### 10.5 テストの保証範囲(統制と実操作の区別)
- g8 は、CDP の実タッチ入力(`Input.dispatchTouchEvent`)で、実際の近接◎のタッチ経路を通している。今回変えたのは「いつ読むか」だけで、入力の経路・時刻は変えていない(g11/g13 の仮想時刻や、一時停止による固定は使っていない)。
- 保証すること: 環状への指で、旋回が目標(-90 度)に達し、その向きにゆっくり進む(速度 < 4)。
- 保証しないこと: 旋回の途中の角度(曲線の形)。旋回の速さ(`turnGain`、`turnRate`)の回帰は別途なし(必要なら、曲線の +0.1 秒の値を判定する統制テストを足す余地がある)。
- 実機 Pixel 7a での操作感は未確認。

## 11. 旋回速度の回帰テスト(2026/11/16)

### 11.1 記録の訂正(待機上限の変更)
ChatGPT の独立監査で、g8 の前回修正に「待機上限 12,000 ms → 60,000 ms」の変更が含まれていることが指摘された。§9.2・§10.4 の「タイムアウトの延長は行っていない」は事実と一致しないので訂正する。

- **性質**: 判定角度・成功率などの**合格基準の緩和ではない**。低速で動く環境(ゲーム内の時間が実時間より遅く進む)で、「状態が遷移するのを待つ」ための**待機の上限**を長くした。待っている条件(例: `prox.on` が false になる、モードが `landed` になる)と、その後の判定は変えていない。遷移しなければ、上限(最大 120 秒)のあとに従来どおり失敗する。ただし、上限を延ばせば、遅い環境で遅れて遷移した場合も合格になるので、**遷移の速さそのものを検査する意図の項目なら、延長は検査を弱める**。下の変更は、いずれも「遷移の有無」を確かめる項目で、速さを確かめる項目ではない(旋回の速さは §11.3 の新しいテストで別に確かめる)。
- **main(c29213a)に対して変えた待機上限の一覧**(`test/browser.mjs`):

| 場所 | 旧 | 新 | 備考 |
| --- | --- | --- | --- |
| g3 着地を待つ(`mode !== "air"`) | 40,000 | 120,000 | 当初の H9 コミットで延長(低速巡航で着地までの飛行時間が約 3 倍) |
| g3 `landed` を待つ | 15,000 | 40,000 | 同上 |
| g8 旋回の完了を待つ | 10,000 | 30,000 | 条件を「-1.2 rad を超えた」から「目標に達した」に変更したため |
| g8 巡航パッドで通常飛行に戻るのを待つ(`!prox.on`) | 12,000 | 60,000 | **前回の g8 修正に含まれていた変更** |
| g8 地上の長押しで浮き上がるのを待つ | 8,000 | 30,000 | 条件に `y > 0.4` を足した |

- そのほか、新しく設けた待機がある(上限は新規): `simWait`(ゲーム内の秒数を待つ。上限 90,000)、g11 のタップ後の効果待ち(2,500)、g15 の仮選択待ち(6,000)、g7 の実タッチ補完(2,500)、g8 の旋回記録待ち(60,000)など。
- 「恣意的な sleep の延長」(固定の `sleep` を長くして偶然通す)は行っていない。固定待ちは、状態・ゲーム内時間で待つ方式に置き換えた。

### 11.2 問題
g8 は旋回の**最終角度**(約 90 度)に着くことは保証するが、**途中の速さ**は保証しない。`turnGain`・`turnRate`・時間積分を変えて旋回が遅く(または速く)なっても、最終角度が -80〜-100 度に入れば合格してしまう。

### 11.3 追加したテスト
1. **固定ステップの純粋な物理テスト**(`test/h1prox.ts`、単体テスト): ゲーム本体と同じ 1/60 秒の固定ステップで、`Flight` に環状(90 度右)・左・外側(120 度)・45 度の指示を与え、1・3・6・12・18・30 ステップ後(1/60、0.05、0.1、0.2、0.3、0.5 秒)の角度を基準曲線と照合する(許容 ±0.2 度)。前進速度に依存しないこと、目標に落ち着くこと、左右が鏡像であることも確かめる。描画フレーム・実時間・入力経路に依存しない、決定的な検査。
2. **実タッチ経路 + 物理ステップごとの記録**(`test/browser.mjs` の g8): CDP の実タッチで近接◎の環状を押し、`Flight.step` を一時的に包んで各物理ステップの「前の向き・後の向き・指示の向き」を記録し、指示の向きが変わったステップを 0 として、同じ 6 点を基準曲線と照合する(許容 ±0.2 度)。記録の包みはテストの中だけで、照合後に `delete` で外す。描画フレームの境界の誤差を受けない。
3. 既存の g8「約 90 度」(最終角度 -80〜-100 度、実タッチ)は維持した(§10.4 の読み取り時点の連動もそのまま)。

### 11.4 基準値と許容の根拠(実測)
- 基準は、過去の報告値ではなく、**今回、同じ条件・同じ入力で、main(c29213a)と H9(c19200f)の両方で実測**した値。**両者は全時点で小数第 2 位まで一致**した。
- 開始から(90 度右、固定ステップ): 1 ステップ -7.16、0.05 秒 -21.49、0.1 秒 -42.97、0.15 秒 -62.32、0.2 秒 -73.98、0.3 秒 -84.63、0.5 秒 -89.40、1.0 秒 -90.00 度。120 度: 0.2 秒 -85.65、0.3 秒 -108.50、0.5 秒 -118.71。45 度: 0.05 秒 -18.72、0.1 秒 -29.79、0.2 秒 -39.91。
- 旋回の前半は `turnRate`(7.5 rad/s = 1 ステップ 7.16 度)の上限、後半は `turnGain`(10)の追従で決まる。
- ブラウザの実タッチ経路の記録は、固定ステップの曲線と **差 0.00 度で一致**した(CPU 1 倍・4 倍、6 点すべて)。
- **許容 ±0.2 度の根拠**: 固定ステップで結果が決定的で、ブラウザでの観測差が 0 だった。感度の実測(基準からのずれ): `turnGain` ×0.9 は 0.2 秒で +1.7 度、×0.8 は +3.9 度、`turnRate` ×0.9 は 0.1 秒で +4.3 度。許容を広げる根拠がない。

### 11.6 保証範囲
